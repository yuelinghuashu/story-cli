# 🎯 设计理念

story-cli 不只是工具，更是一套写作工作流哲学。

---

## 🪶 一切皆文件

**故事就是文件夹 + Markdown 文件。**

- 故事 = `NN-名称/` 目录 + `config.json`（元数据）+ `text.md`（正文）
- 元数据是可读的 JSON，正文是纯 Markdown
- 目录结构天然反映内容结构

这让故事库**天然兼容 Git 的一切能力**：

| Git 能力   | 对写作的意义                           |
| ---------- | -------------------------------------- |
| `git diff` | 查看某次改动的具体行，精准回溯         |
| `git log`  | 按时间线回顾创作历程                   |
| `git tag`  | 标记完结、番外、特别版                 |
| `git grep` | 全库搜索台词、人物、场景               |
| 分支/PR    | 激进改稿也能安全回退，多人协作文档审查 |

不需要数据库、不需要云端同步、不需要专有格式。**你的故事永远是普通文件**，任何工具、任何编辑器、任何时间都能打开。

---

## ⚡ 零依赖心智负担

**仅 2 个运行时依赖**：`fflate`（EPUB ZIP 打包）和 `handlebars`（模板渲染）。

- 不引入 `commander`/`yargs` — 参数解析 50 行手写足够
- 不引入 `marked`/`markdown-it` — Markdown 转换器 180 行手写满足写作需求
- 不引入测试框架 — `node:test` 零依赖
- 不需要编译步骤 — 开发时 Node 24+ 原生运行 TypeScript；发布产物为编译后 JS（兼容 Node >= 20）

**为什么坚持手写而非引入成熟库？**

1. **依赖即责任** — 每个依赖都有自己的 bug、版本迁移和供应链风险
2. **工具链可控** — 手写 180 行转换器，出问题 10 分钟就能定位修复
3. **功能够用就好** — 小说写作需要的 Markdown 子集是明确的，不需要通用解析器的全部能力
4. **安装即用** — 用户 `pnpm i` 秒装，`story build` 直接跑

代价是边界情况处理不如成熟库（嵌套引用、复杂转义），但这通过**边界测试兜底**（见 `tests/md-to-html.test.ts`），而不是通过引入依赖解决。

---

## 🚀 零部署

**build 的产物（README / HTML / EPUB）都是纯静态文件。**

- 故事 README → GitHub 自带渲染
- 根索引 README → GitHub 仓库首页
- HTML 导出 → 任意静态托管（GitHub Pages / Vercel / 任意 HTTP 服务器）
- EPUB → 本地阅读 / 分发

不需要服务器、不需要数据库、不需要构建服务。**`story build` 的输出放哪都能读。**

---

## 📐 约定优于配置

**目录结构就是内容结构。**

```text
仓库/
├── 01-故事A/
│   ├── config.json      # 元数据（标题/类型/状态/字数）
│   └── text.md          # 正文（或 chapter-*.md 分章）
├── 02-故事B/
└── assets/sponsor/      # 赞助收款码
```

用户需要理解的概念：

1. 目录名以 `NN-` 开头就是故事
2. `config.json` 写元数据
3. `text.md` 写正文

**仅此而已。** 不需要学配置语法、不需要理解数据库模型、不需要概念映射。5 分钟上手，写就完了。

## 🇨🇳 中文优先

**面向中文创作者的设计，同时完整支持英文。**

- 中文字数统计（按汉字计数，而非字符数）
- 中英双语文案（`LANG` 环境变量自动检测）
- 双语文档（每个文档都有中英版本）
- 中英混合写作（`language` 字段按故事配置）
- 中文友好的文件名处理（保留中文标题用于 README 展示）

## 🔄 与现有工具的设计方向

故事管理 / 写作工具大致有几个方向：

| 方向             | 典型特征                                       | 目标用户               |
| ---------------- | ---------------------------------------------- | ---------------------- |
| 云出版平台       | 托管 + GUI 编辑器 + 团队协作，内容进入平台格式 | 团队、内容创作者       |
| 静态文档站生成器 | 本地生成 + 主题系统 + 插件生态，通用文档场景   | 开发者、文档作者       |
| 通用格式转换器   | 格式互转能力强，覆盖广泛输入输出               | 学术、跨格式需求者     |
| 网文写作软件     | 编辑器 + 云同步 + 平台分发                     | 网络小说作者           |
| 本地知识库       | GUI + 双向链接 + 知识图谱 + 插件生态           | 笔记、知识管理爱好者   |
| **story-cli**    | Git 原生 + Markdown 零依赖 + CLI 驱动          | Git 用户、开发者创作者 |

每种方向都有各自的目标用户。story-cli 不替代任何方向——它为「希望在 Git 中直接管理故事文件」的人提供了一条专门的道路。

## 🧭 什么场景适合 / 不适合

### 适合

- 喜欢用 Git 管理一切的开发者
- 用 Markdown 写作的创作者
- 需要中英双语讲故事的人
- 希望故事长期可追溯、可迁移的人
- 对"数据在别人手里"有顾虑的人

### 不适合

- 需要 GUI 编辑器的写作新手
- 需要云同步 / 多设备实时协作的重度写手
- 需要一键发布到网文平台的作者
- 需要富媒体排版（插图、字体、复杂版式）的作者

**story-cli 不是要取代写作软件，而是为「文件即所有权」的人提供一个与 Git 深度绑定的写作工作流。**
