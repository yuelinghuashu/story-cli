# 🎯 设计理念

story-cli 不只是工具，更是一套写作工作流哲学。

---

## 🪶 一切皆文件

**故事就是文件夹 + Markdown 文件。**

- 故事 = `NN-名称/` 目录 + `config.json`（元数据）+ `text.md`（正文）
- 元数据是可读的 JSON，正文是纯 Markdown
- 目录结构天然反映内容结构

这让故事库**天然兼容 Git 的一切能力**：

| Git 能力   | 对写作的意义                           |
| ---------- | -------------------------------------- |
| `git diff` | 查看某次改动的具体行，精准回溯         |
| `git log`  | 按时间线回顾创作历程                   |
| `git tag`  | 标记完结、番外、特别版                 |
| `git grep` | 全库搜索台词、人物、场景               |
| 分支/PR    | 激进改稿也能安全回退，多人协作文档审查 |

不需要数据库、不需要云端同步、不需要专有格式。**你的故事永远是普通文件**，任何工具、任何编辑器、任何时间都能打开。

---

## ⚡ 零依赖心智负担

**仅 2 个运行时依赖**：`fflate`（EPUB ZIP 打包）和 `handlebars`（模板渲染）。

- 参数解析使用 Node 内置 `util.parseArgs`（零依赖）
- Markdown 转换器使用约 180 行自制实现（覆盖小说写作所需子集）
- 测试使用 Node 内置 `node:test`（零依赖）
- 不需要编译步骤 — 开发时 Node 24+ 原生运行 TypeScript；发布产物为编译后 JS（兼容 Node >= 22）

细节由**边界测试兜底**（见 `tests/md-to-html.test.ts`），而不是通过引入依赖解决。

---

## 🚀 零部署

**build 的产物（README / HTML / EPUB）都是纯静态文件。**

- 故事 README → GitHub 自带渲染
- 根索引 README → GitHub 仓库首页
- HTML 导出 → 任意静态托管（GitHub Pages / Vercel / 任意 HTTP 服务器）
- EPUB → 本地阅读 / 分发

不需要服务器、不需要数据库、不需要构建服务。**`story build` 的输出放哪都能读。**

---

## 📐 约定优于配置

**目录结构就是内容结构。**

```text
仓库/
├── 01-故事A/
│   ├── config.json      # 元数据（标题/类型/状态/字数）
│   └── text.md          # 正文（或 chapter-*.md 分章）
├── 02-故事B/
└── assets/sponsor/      # 赞助收款码
```

用户需要理解的概念：

1. 目录名以 `NN-` 开头就是故事
2. `config.json` 写元数据
3. `text.md` 写正文

**仅此而已。** 不需要学配置语法、不需要理解数据库模型、不需要概念映射。5 分钟上手，写就完了。

## 🧮 分数索引：物理坐标与逻辑坐标的分离

**这是 story-cli 排序设计的核心：为什么文件夹序号永远不变，但展示顺序却可以自由调整？**

### 问题：加法排序的困境

传统故事库按文件夹序号排序（`01-` / `02-` / `03-`）：

```text
01-故事A
02-故事B
03-故事C
```

如果想在 `故事B` 和 `故事C` 之间插入新故事 `故事B2`，你必须**重命名** `03-故事C → 04-故事C`。重命名的代价：

- 所有指向 `03-故事C` 的链接（README、EPUB 引用、外部引用）全部失效
- Git 历史显示为「删除 + 新增」而非连续修改
- 多人协作时重命名引发合并冲突

**这就是「物理坐标」的典型困境：序号是内容的身份，重排意味着破坏身份。**

### 解法：物理坐标 + 逻辑坐标分离

| 坐标类型     | 载体                                        | 特征                                   |
| ------------ | ------------------------------------------- | -------------------------------------- |
| **物理坐标** | 文件夹名 `NN-` 前缀                         | 一旦创建永不修改，是故事的「身份证号」 |
| **逻辑坐标** | `config.json` 中的 `series` / `seriesOrder` | 随时可调，是故事的「座位号」           |

**物理坐标决定文件在哪，逻辑坐标决定展示顺序。**

### 为什么 `seriesOrder` 要支持小数？

假设系列现有排序 `1, 2, 3`，你想在 `2` 和 `3` 之间插入新故事：

```json
{
  "title": "新插入的故事",
  "series": "三体",
  "seriesOrder": 2.5
}
```

**根 README 展示顺序变为：`1 → 2 → 2.5 → 3`**

- 你**不需要修改**任何已有故事的 `seriesOrder`
- 你**不需要重命名**任何文件夹
- 所有现有链接保持稳定

这就是**分数索引**（Fractional Indexing）——源自数据库设计中的浮点排序键思想。类比：

| 场景                   | 排序方式                                                        |
| ---------------------- | --------------------------------------------------------------- |
| 数据库行插入           | `position = (prev.pos + next.pos) / 2`                          |
| Git 提交时间           | 时间戳天然可插入（随时替换中间值）                              |
| **story-cli 系列顺序** | `seriesOrder` 数字永不排比（支持 `2.5` 插入在 `2` 和 `3` 之间） |

### 极限情况

- **理论上无限插入**：小数没有最小间隔，`2.5` → `2.25` → `2.125` → ... 可以无限细分下去
- **实际建议**：每本书的系列通常在 10 部以内，用整数 + 一位小数绰绰有余
- **失败模式**：如果 `seriesOrder` 是 9.999999... 导致浮点精度问题，可以重编号（这是逻辑坐标，随时可调，无破坏性）

### 核心获益

- **增加故事**：永远不需要重排已有内容
- **删除故事**：序号空缺自动忽略，无需补位
- **调整顺序**：只改一个 JSON 字段，不碰文件夹名
- **Git 稳定**：文件夹名永不变 → 链接永不失效 → 历史连续可追踪

## 🌐 双语优先

**为中文和英文创作者提供对等的体验，当前覆盖中英双语，结构上可扩展更多语言。**

- 语言感知字数统计（中文按汉字，英文按单词）
- 中英双语文案（`LANG` 环境变量自动检测）
- 双语文档（每个文档都有中英版本）
- 中英混合写作（`language` 字段按故事配置）
- 中文友好的文件名处理（保留中文标题用于 README 展示）

> 设计上预留多语言扩展空间：`language` 字段和 i18n 模块可以轻松添加更多语言。

## 🧰 工具箱，而非一体化套件

**story-cli 刻意不做 GUI，不内置 AI。**

不是做不到，而是故意不碰。编辑器体验（语法高亮、实时预览、拼写检查）已被 VS Code / JetBrains / Neovim 打磨到了极致，AI 辅助（补全、续写、润色）已被 Copilot / Cursor / Continue 等工具覆盖。story-cli 就算花十年也追不上这些领域的专业产品。

### 通过文件系统解耦

编辑器和 CLI 之间唯一的接口是**文件**：

```text
text.md        ← 用任何编辑器写正文（VS Code 实时预览、Copilot 续写都行）
config.json    ← 用任何工具改元数据（标题、类型、状态、系列）
story build    ← CLI 只管治理与构建（校验、README、EPUB）
```

- 你可以用 VS Code + Markdown Preview Enhanced 实时预览章节
- 你可以用 GitHub Copilot / Cursor 辅助写作高潮段落
- 你可以切换 JetBrains、Neovim、任何未来出现的编辑器——**工具链无缝，数据共通**

### "集成"常常是"锁定"的代名词

| 工具           | 数据模式              | 换工具的成本                                |
| -------------- | --------------------- | ------------------------------------------- |
| Scrivener      | .scriv 专有格式       | 数据无法迁移，只能继续用 Scrivener          |
| Obsidian 插件  | 本地 .md（开放）      | GUI 为核心，插件生态绑定 Obsidian           |
| 某些 AI 写作台 | 云端或专有格式        | 深度绑定特定模型 API，模型下线工具链即崩    |
| **story-cli**  | 纯文件（.md + .json） | 任何编辑器 + 任何 AI 工具 + 任何 Git 工作流 |

story-cli 完全不碰 AI：你想用 Claude 还是 DeepSeek，去编辑器里装插件；你想用 Copilot 还是 Cursor，随意。CLI 只忠实地处理你写好的文本，**绝不绑架你的 AI 工作流或编辑习惯**。

### Unix 哲学：do one thing, and do it well

编辑器管创作体验，CLI 管内容治理，两者通过文件系统解耦。这是 Unix 哲学在创作工具领域的经典实践——**每个工具做好一件事，组合起来就是完整工作流**。

### 长期可维护性

"胶水层"（把优秀基础设施粘合起来）的寿命往往长于"全栈解决方案"。只要 Markdown 和 JSON 不消亡，`story new` / `story epub` 就能一直用下去。VS Code 会迭代、AI 模型会换，但你的故事文件夹结构永远稳定——核心数据（文件）和核心逻辑（CLI）始终掌握在自己手里。

### 原子能力与工作流编排

**CLI 做原子能力，Makefile 做工作流编排。**

用户的真实使用场景从来不是单条命令，而是「新建 → 构建 → 提交 → 推送」这样的链条。story-cli 的每个命令（`story new` / `story build` / `story stats`）都是**原子能力**——它们做的事单纯、可预测、可组合。

`story init` 会额外生成一个**可编辑的 Makefile**，将高频操作组合封装为工作流入口：

```bash
make help                      # 查看所有可用命令
make new TITLE="我的新故事"     # 创建故事 + 自动构建
make commit                    # 构建 + git add + git commit
make push                      # 构建 + 提交 + 推送
make stats                     # 创作统计
make epub                      # 导出全部 EPUB
```

**为什么不让 CLI 直接支持 `--commit` / `--push`？**

1. **Unix 哲学**：每个工具做一件事，做好。CLI 不应该是"万能执行器"
2. **用户可定制**：Makefile 可以自由添加自己的 hook（如 commit 前跑脚本、push 前发通知）
3. **不自锁**：不穷举所有可能的"链条组合"——用户有需求时直接改 Makefile

**分工边界**：

| 层       | 工具        | 职责                   | 示例                                |
| -------- | ----------- | ---------------------- | ----------------------------------- |
| 工作流   | `Makefile`  | 组合多个步骤、处理依赖 | `make push` = build + commit + push |
| 原子能力 | `story` CLI | 单一步骤、做好一件事   | `story build` / `story stats`       |
| 领域逻辑 | `src/` 模块 | 扫描 / 校验 / 渲染     | `scanner.ts` / `validate.ts`        |

## 🔄 与现有工具的设计方向

故事管理 / 写作工具大致有几个方向：

| 方向              | 典型特征                                       | 目标用户               |
| ----------------- | ---------------------------------------------- | ---------------------- |
| 云出版平台        | 托管 + GUI 编辑器 + 团队协作，内容进入平台格式 | 团队、内容创作者       |
| 静态文档站生成器  | 本地生成 + 主题系统 + 插件生态，通用文档场景   | 开发者、文档作者       |
| 通用格式转换器    | 格式互转能力强，覆盖广泛输入输出               | 学术、跨格式需求者     |
| 网文写作软件      | 编辑器 + 云同步 + 平台分发                     | 网络小说作者           |
| 本地知识库        | GUI + 双向链接 + 知识图谱 + 插件生态           | 笔记、知识管理爱好者   |
| AI 写作助手       | 云端模型 + 续写/润色 + 平台绑定                | 追求写作灵感的作者     |
| 编辑器 + CLI 组合 | 编辑器管创作 + CLI 管治理，文件系统解耦        | Git 用户、开发者创作者 |
| **story-cli**     | Git 原生 + Markdown 零依赖 + CLI 驱动          | Git 用户、开发者创作者 |

每种方向都有各自的目标用户。story-cli 不替代任何方向——它为「希望在 Git 中直接管理故事文件」的人提供了一条专门的道路。

## 🧭 什么场景适合 / 不适合

### 适合

- 喜欢用 Git 管理一切的开发者
- 用 Markdown 写作的创作者
- 需要中英双语讲故事的人
- 希望故事长期可追溯、可迁移的人
- 对"数据在别人手里"有顾虑的人
- 希望自由选择编辑器、AI 工具和写作工作流的人

### 不适合

- 希望在单一软件内完成一切（编辑 + 管理 + 发布）的人
- 需要云同步 / 多设备实时协作的重度写手
- 需要一键发布到网文平台的作者
- 需要富媒体排版（插图、字体、复杂版式）的作者

**story-cli 不是要取代写作软件，而是为「文件即所有权」的人提供一个与 Git 深度绑定的写作工作流。**
